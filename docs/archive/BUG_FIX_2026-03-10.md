# Bug Fix: Poll Answer Persisting Between Back-to-Back Polls

**Date**: March 10, 2026
**Status**: ✅ Fixed
**Affected Components**: Attendee App - All activity components

## Problem Description

When two polls (or any activities of the same type) were placed back-to-back in a presentation, the attendee's answer from the first activity would incorrectly appear pre-selected in the second activity.

**Example scenario:**
1. Presenter shows Poll 1: "How are you feeling?"
2. Attendee selects "Great!" and submits
3. Presenter immediately shows Poll 2: "What's your favorite color?"
4. **BUG**: "Great!" is still selected on Poll 2

**Workaround that worked:**
- If presenter navigated to a different activity type (e.g., quiz, web-link) and then back to Poll 2, the state would reset correctly.

## Root Cause

The issue was in `/packages/attendee-app/src/App.tsx` in the `WaitingContent` component (lines 41-63).

React was reusing the same component instance when switching between activities of the same type. The component tree looked like this:

```
WaitingContent
  └─ <Poll /> (for Poll 1)

// When switching to Poll 2:
WaitingContent
  └─ <Poll /> (same component instance, just updated props)
```

Since React didn't unmount and remount the `Poll` component, all local state persisted:
- `selectedOptions` array (Poll.tsx line 19)
- `submitted` boolean (Poll.tsx line 20)
- `response` text (TextResponse.tsx line 25)
- `selectedOption` (Quiz.tsx line 18)
- etc.

**Why it worked when navigating through another activity:**
When going Poll 1 → Quiz → Poll 2, React would unmount `<Poll />` and mount `<Quiz />`, then unmount `<Quiz />` and mount a fresh `<Poll />`, which reset all state.

## Solution

Added a `key` prop to force React to unmount/remount activity components when the activity changes.

**File changed:** `/packages/attendee-app/src/App.tsx`

```typescript
const WaitingContent: React.FC = () => {
  const { currentActivity, currentResults } = useSocket();

  if (currentActivity) {
    // Use activityId as key to force remounting when switching between activities
    // This ensures component state (like selected answers) is reset between activities
    const activityKey = currentActivity.activityId || `${currentActivity.type}-${Date.now()}`;

    switch (currentActivity.type) {
      case 'poll':
        return <Poll key={activityKey} activity={currentActivity as any} results={currentResults as any} />;
      case 'quiz':
        return <Quiz key={activityKey} activity={currentActivity as any} />;
      case 'web-link':
        return <WebLink key={activityKey} activity={currentActivity as any} />;
      case 'text-response':
        return <TextResponse key={activityKey} activity={currentActivity as any} />;
      case 'review-game':
        return <ReviewGame key={activityKey} activity={currentActivity as any} />;
      default:
        return <WaitingScreen />;
    }
  }

  return <WaitingScreen />;
};
```

**How it works:**
- Each activity has a unique `activityId` (e.g., "poll-1", "poll-2", "quiz-1")
- By setting `key={activityKey}`, React treats each activity as a distinct component instance
- When switching from Poll 1 to Poll 2, React sees different keys and completely unmounts Poll 1 and mounts a fresh Poll 2 instance
- All state (`selectedOptions`, `submitted`, etc.) starts fresh

**Fallback logic:**
If `activityId` is missing, we use `${currentActivity.type}-${Date.now()}` to ensure a unique key.

## Why This Is Better Than The Quiz Workaround

The Quiz component (Quiz.tsx lines 27-37) had a manual workaround using `useEffect` and a ref:

```typescript
const lastActivityIdRef = useRef<string | undefined>(activity.activityId);

useEffect(() => {
  if (lastActivityIdRef.current !== activity.activityId) {
    console.log('New quiz question detected, resetting state');
    lastActivityIdRef.current = activity.activityId;
    setSelectedOption(null);
    setSubmitted(false);
    setResult(null);
    setTimeLeft(activity.timeLimit ? activity.timeLimit : null);
  }
}, [activity.activityId, activity.timeLimit]);
```

**Problems with the manual approach:**
1. More complex and harder to maintain
2. Requires manually resetting each piece of state
3. Easy to forget to reset new state variables
4. Doesn't work for Poll/TextResponse (they didn't have this logic)
5. Potential race conditions with timers and async operations

**Benefits of the `key` prop approach:**
1. Simple, React-idiomatic solution
2. Works for ALL activity types automatically
3. Guaranteed fresh component state
4. No manual cleanup needed
5. Prevents all types of state leakage
